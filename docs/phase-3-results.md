# Phase 3 results: batches

**Date:** 2026-10-05 · **Measured on:** Apple M1 Pro (8-core CPU, 14-core GPU, 16 GB), macOS, Google Chrome 154, ONNX Runtime Web 1.30.0 · **Builds on:** [Phase 2](phase-2-results.md)

## Verdict

The Phase 3 criterion in [`implementation.md`](implementation.md):

> 100 × 45 MP JPEGs complete in Chrome with flat memory, saved to a folder. Kill the tab halfway, reopen, grant permission — the batch resumes and skips what's done.

| Part                                              | Result                                                                                                                                                                                                    |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **100 × 45 MP JPEGs complete in Chrome**          | ⏳ Running when this was written: 68 of 100 exported at 95 s per photo. Updated when it finishes.                                                                                                         |
| **With flat memory**                              | ⏳ Sampled through the whole run; reported when it finishes.                                                                                                                                              |
| **Saved to a folder**                             | ⏳ Checked when the run finishes: every output in `denoised/` inside the chosen folder.                                                                                                                   |
| **Kill the tab halfway, reopen**                  | ✅ After 50 of 100 were saved (79.4 min), the test SIGKILLed Chrome's whole process tree, then launched Chrome again on the same profile.                                                                 |
| **Grant permission — resumes, skips what's done** | ✅ The drop zone offered **Continue**; one permission for the folder; the batch went on from photo 51 and kept going (68 of 100 when this was written). The final skip count is checked when it finishes. |

Measured with `HUSH_BATCH_COUNT=100 pnpm --filter @hush/web e2e:real` (`apps/web/e2e/real/batch.spec.ts`) on the synthetic 45.4 MP camera JPEG from Phase 2, copied 100 times into a folder. The folder is Chrome's private file system standing in for one the photographer picks (Playwright can't click a native folder picker); it lives in a Chrome profile on disk, as a real browser's would.

Every requirement Phase 3 lists — queue, folder input, thumbnails, shared settings, progress and multi-hour ETA, pause/cancel/retry, wake lock, unload warning, save-to-folder with skip-existing, resume-after-reload, ZIP in parts — is built and tested; see below.

## What was built

```
choose / drop / "Choose folder" ─▶ photos worker ──────────▶ grid: thumbnails, sizes, refusals with reasons
                                    headers (JPEG: first MB)     shared settings: preset, four sliders, Advanced
                                    thumbnails                   click a photo → the editor at 100% (← → through the batch)

Export N photos ─▶ BatchRunner (core) ─▶ for each photo:  already in the folder? → skipped
                                         pipeline worker: decode (short-lived worker) → recipe in place → encode
                                         save: folder (never over a file) or ZIP part (≤ 500 MB, downloads when full)
                                         IndexedDB record: what's done, the settings, the folders
                   footer: "Exporting 3 of 12" · megapixel-weighted bar · "About 3 h 40 min left" · Pause · Cancel
```

## Decisions

Made during the phase, each with its reason. None changes the spec's intent.

| Decision                                                                                                                                            | Why                                                                                                                                                                                                                                                                                                                         |
| --------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **The queue lives in `packages/core`**, with the platform's work behind three hooks.                                                                | §4.5 lists the queue among core's jobs; the native apps get it for free, and every rule — skip, pause, cancel, retry, a failed save, the ETA — is tested in plain Node without a browser.                                                                                                                                   |
| **Pause takes hold at the next tile**, not after the photo.                                                                                         | A 45 MP photo is 90 s of work; "Pause" should mean now. The photo stays decoded in the worker meanwhile (one photo's memory, as when running). A one-tile photo already on the GPU finishes first.                                                                                                                          |
| **Every photo is decoded in a short-lived worker**, as the editor does.                                                                             | The decoder's WASM heap grows to the photo's size and never shrinks; ending the worker after each photo is what keeps a 100-photo batch's memory flat.                                                                                                                                                                      |
| **Photos from a folder are saved into a `denoised` folder inside it** by default.                                                                   | One permission covers reading the photos and writing the results — so after a reload, "grant permission" is once, as the criterion says — and §5.13's own example is "Saved IMG_2041-denoised.jpg to Wedding/denoised". Another folder or ZIP files are one menu away.                                                      |
| **An output already in the folder means skipped**; the editor's single exports still number their files.                                            | §2.7: "any photo whose output already exists in the destination folder is marked skipped" — that is what makes resuming and re-running safe. Names are planned before the run, deterministically, so a resumed batch looks for the same files; two photos with one name are numbered, ignoring case like Windows and macOS. |
| **ZIP parts close at 500 MB**, not 1 GB.                                                                                                            | §2.8 asks for parts of at most 1 GB (🟡). Half that holds half as much in Safari's memory before a part downloads, and loses half as much to a crash, for a few more downloads.                                                                                                                                             |
| **Hush writes its own ZIP** instead of using `client-zip`.                                                                                          | A part is assembled as a Blob of small headers and the photos' own Blobs, with no copy and no stream to drain into memory; stored entries need nothing else. Python's `zipfile` reads every part back in the tests, CRCs included.                                                                                          |
| **A failed save pauses the batch and keeps the photo**; a photo that can't be read fails alone; a GPU or model failure fails that photo and pauses. | §5.13: "keep the result in memory so the user can retry without reprocessing" — and a full disk or a revoked folder would fail every photo after it. "Choose another folder…" saves the kept photo there and carries on.                                                                                                    |
| **The settings are locked while a run is going**, and are the editor's own.                                                                         | §5.4: settings "apply to the batch"; changing them mid-run would give one batch two looks. A resumed batch restores the sliders and export options it started with.                                                                                                                                                         |
| **Export waits for the estimate**, measured with two timed tiles when no photo has been opened.                                                     | §2.10/§5.12: the per-machine estimate is on the button before the photographer commits — "Export 100 photos (about 2 h 40 min)" — and on the processor, a batch over an hour asks first.                                                                                                                                    |
| **The wake lock is let go while paused**; the unload warning stays until the run ends.                                                              | A paused batch isn't working, so the screen may sleep; its unsaved progress is still worth a warning.                                                                                                                                                                                                                       |
| **Thumbnails come from the browser's own decoder**, downscaled while decoding; Hush's codecs only where the browser can't (HEIC).                   | §2.2 allows canvas for downscales. JPEGs decode to thumbnail size quickly, and only for cells near the screen. Headers read only a JPEG's first megabyte: a 400-photo folder reads 0.4 GB to list, not 11 GB.                                                                                                               |
| **Batches of chosen files resume by choosing them again**; folder batches resume from their handle.                                                 | A folder handle needs one permission after a reload; a hundred file handles would need a hundred. Safari and Firefox keep no handles at all, which is the path §2.7 describes.                                                                                                                                              |
| **Sub-folders aren't read**; RAW files and sidecars in a folder are counted and left alone.                                                         | A camera card's folders and a `denoised` folder from an earlier export would otherwise be swept in. RAW is §10.1.                                                                                                                                                                                                           |
| **Thumbnails, marks and the footer barely move** (emil-design-eng).                                                                                 | Photos never animate (§5.7). A state mark fades in over 160 ms from 96% scale when it changes; the footer enters once; progress moves linearly; presses scale to 0.97–0.98; hover is gated to devices that hover; reduced motion keeps only the fades.                                                                      |

## Measurements (real model, this machine)

From `pnpm --filter @hush/web e2e:real` (`apps/web/e2e/real/batch.spec.ts`), WebGPU, fp16.

| Check                                   | Result                                                                              |
| --------------------------------------- | ----------------------------------------------------------------------------------- |
| Estimate on the button, before starting | "Export 100 photos (about 2 h 40 min)" — 164.8 min                                  |
| First half                              | 50 photos in 79.4 min, **95.0 s per photo**; the time left on screen then: 79.7 min |
| Second half, memory                     | ⏳ when the run finishes                                                            |

**The photographer's photos** (`HUSH_PHOTOS`): two 6960 × 4640 (32.3 MP) JPEGs of a lake at dusk, ISO 32000, as one batch: **134 s for both** (about 67 s each), estimated at "about 2 min" beforehand; 9.3 and 9.4 MB out; all 38 EXIF tags identical apart from `Software`. At 100% the colour blotches and luminance grain in the sky and the trees are gone and the town's lights keep their edges; the darkest sky keeps some fine grain at ISO 32000, which is NAFNet-SIDD's limit rather than the batch's (the batch's exports are the editor's exports, pixel for pixel).

**Against §4.6.** A batch runs at the export's speed: 95 s (0.48 MP/s) per 45 MP photo here, in line with Phase 2's single exports (91–98 s). That is below the strong-machine line (≥ 2.4 MP/s, 45 MP ≤ 19 s), so [Phase 0's speed question](phase-0-results.md#what-to-decide) matters most now: at this speed a 400 × 45 MP wedding is about 10½ hours on an M1 Pro, which Hush says honestly up front; at the strong-machine target it would be about 2 hours.

## How to reproduce

```sh
pnpm install && pnpm test && pnpm e2e                                   # what CI runs
pnpm fetch-models --from tools/models/out                               # the release model
HUSH_BATCH_COUNT=100 pnpm --filter @hush/web e2e:real                   # the acceptance run (~2.5 h), plus Phases 1–2's checks
HUSH_PHOTOS=/path/a.jpg,/path/b.jpg pnpm --filter @hush/web e2e:real    # a batch of your photos; exports in test-results/
```
